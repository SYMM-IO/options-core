This note collects the redesign conversation of 2026-10-02 and the six research notes next to it. It is a brainstorm. Nothing here is decided, and the contract sketches are illustrations.

The request

Naveed wants options-core rebuilt around three ideas.

  1. A small accounting core that knows nothing about options or perps. Addresses own pools. An upper layer tells the core to move funds from one pool to another, and the core makes sure that happens.
  2. A generic intent layer. An intent carries rules, and each rule is a validator address plus bytes. Ivy vaults already use this shape for bid rules. The core never interprets a rule.
  3. Off-chain speed with on-chain guarantees. User and solver sign things off-chain. The chain gets a write every few minutes. Funds never leave the chain. The solver can hedge without racing the chain. The user can get their money in bounded time even if the solver turns hostile.

Assumptions I made that Naveed still needs to confirm:

  • Collateral committed to one solver is not shared with another solver.
  • This is a fresh design. It does not need to stay compatible with deployed Symmio contracts.
  • It deploys on EVM L2s, where gas is cheap but not free.
  • Muon stays available as one oracle choice and is not mandatory.

Where the code is today

  • options-core is one Diamond. Opening a position takes three transactions: sendOpenIntent, lockOpenIntent, fillOpenIntent. The InstantLayer can batch signed calls into one transaction, but the Diamond still executes every call.
  • Accounting, the intent state machines and the option logic share storage and call each other directly.
  • Some pieces of the new idea already exist. crossBalance[counterparty] is a per-solver bucket. Instant action mode blocks the user's direct calls and takes a cooldown to leave. perps-core 0.8.6 has bind mode, where a user binds to one solver and that solver trades without Muon signatures.
  • Bind mode buys speed with trust. Its own docs say the bound solver "can then pass any value they choose to the contract method".
  • Trust is concentrated elsewhere too. The Diamond owner can replace any facet. The clearing house role picks liquidation prices. Muon signs uPnL and settlement prices.

The codebase has been moving toward "one user paired with one solver" for a while. The redesign makes that pairing the foundation, and it removes the need to trust the solver inside the pairing.

The main idea: the chain is the court and the escrow, not the ledger

Today the chain records every step of every trade. That is why every step costs gas, and why the solver has to win a race against the chain.

The contracts only have three jobs.

  1. Custody. The funds exist and nobody can pledge them twice.
  2. Commitment. One party cannot deny or change what both agreed.
  3. Resolution. When they disagree, or one disappears, funds still move the way the agreement says.

Matching, pricing, quoting, hedging and risk checks can all happen off-chain.

The observation that makes this safe: in a bilateral system with separated collateral, a state signed by both parties needs no further validation. Nobody else's money is involved. Re-executing the trade on-chain adds gas and no safety. Product logic only has to run on-chain when the two parties disagree.

There is one exception. Fees owed to third parties, the platform and affiliates, are somebody else's money. See the hard problems section.

Why the race happens and what removes it

The race today: the solver reads chain state, hedges on Binance, then sends the fill. In between, the user withdraws or trades with another solver. The fill reverts and the solver holds a hedge it does not want.

The cause is that the collateral behind the fill sits in state that someone else can change at once, without the solver's consent.

One rule fixes it. Inside a channel, anything that reduces one party's protection needs that party's signature, or a notice period long enough for them to react. Adding collateral needs neither.

The user cannot pull collateral out from under a signed intent. The solver signs a fill knowing the state cannot move. Nobody sends a lock transaction, because the channel is the lock.

The cost is that collateral is split per solver. Allocated balances work the same way today, so this is not a regression.

Vault

  • A pool is (owner, id), with a balance per token. The owner deposits and withdraws free balance at will.
  • The owner can commit funds to a controller under a key. Only that controller can move or release committed funds.
  • The vault has no product knowledge, no oracle, and no role with power over user funds. It can be small enough to be immutable.

A sketch of the interface, to show its size:

interface IVault {
	function deposit(bytes32 pool, address token, uint256 amount) external;
	function withdraw(bytes32 pool, address token, uint256 amount, address to) external;
	function commit(bytes32 pool, address controller, bytes32 key, address token, uint256 amount) external;

	// callable only by the controller that holds the commitment
	function move(bytes32 fromKey, bytes32 toKey, address token, uint256 amount) external;
	function release(bytes32 key, bytes32 pool, address token, uint256 amount) external;
}

Channel

The channel controller is the first controller. A channel links two pools and holds what each committed.

On-chain, per channel: the two pools, the token, the adjudicator address, the challenge period, one signer key per side, cumulative deposits and withdrawals per side, and the version and hash of the last checkpoint.

Off-chain, signed by both sides:

struct ChannelState {
	bytes32 channelId;
	uint64 version; // only goes up
	int256 netAtoB; // cumulative cash moved from A to B: premiums, realised PnL, fees
	uint256 withdrawableA; // cumulative amount A may take out
	uint256 withdrawableB;
	bytes32 positionsRoot; // open positions, each leaf is {engine, data}
	bytes32 feesRoot; // cumulative fees owed to third parties
}

netAtoB is cumulative on purpose. A deposit lands on-chain without needing a new signed state, and an old proof can never pay twice.

Money moves in three ways.

  1. Both sign. The checkpoint applies at once.
  2. One party submits the latest co-signed state and waits out the challenge window. During the window anyone holding a newer co-signed state can replace it. The window answers one question only: is there a newer state?
  3. Whatever the frozen state does not settle by itself goes to the adjudicator, which rules on positions using their data and oracle proofs.

Smart-account signatures can change meaning over time, because ERC-1271 is evaluated when the call happens. So each side registers a plain signing key for the channel when it opens. That key doubles as the session key that lets a front-end sign at speed.

Adjudicator and engines

The adjudicator is a contract address fixed when the channel opens. Changing it takes both signatures. Each channel knows its judge before the first trade.

  • The first adjudicator runs fully on-chain. It takes revealed positions and calls one engine per position.
  • An engine is a product module. It answers two questions: what does this position pay given this oracle proof, and how much must stay locked until it settles.
  • Later adjudicators can accept a Muon attestation of whole-book margin, or a validity proof, without touching the vault or the channel.
interface IEngine {
	// payout owed by one side to the other for a position, given an oracle proof
	function settle(bytes calldata position, bytes calldata oracleProof) external view returns (int256 amountAtoB, bool isFinal);

	// what each side must keep locked while the position is open
	function locked(bytes calldata position) external view returns (uint256 lockedA, uint256 lockedB);
}

Options and perps are two engines. A new product is a new engine. The vault and the channel do not change.

Intents and rules

An intent is a message the user signs. It authorises the solver to move the channel to a new state that satisfies the rules.

struct Rule {
	address validator;
	bytes4 kind; // lets one validator serve several rule types, as in Ivy
	bytes data;
}

struct Intent {
	bytes32 channelId;
	uint256 nonce;
	uint64 deadline;
	Rule[] rules;
	bytes32 payloadHash; // the order itself, read only by validators and engines
}
  • Validators are view functions, called with STATICCALL, the way Ivy's IIvyBidValidator works.
  • Both sides run the validators off-chain with eth_call. The bytecode stays the single definition of what a rule means.
  • A validator only runs inside a transaction when someone disputes a fill.
  • The solver signs a fill. The user's client acknowledges it by co-signing the new state. If the user does not answer, the solver posts the fill on-chain before the deadline plus a short grace period, and that makes it binding.

Solvers keep the flow they have today: see a binding intent, hedge, then fill. The difference is that the fill is a signature, not a transaction.

A trade from start to finish

A call option is a paid right to buy at a fixed price later. Alice pays 50 USDC today for the right to buy 1 ETH at 3,000 next Friday. If ETH is at 3,200 on Friday, that right is worth 200. If ETH is below 3,000, it is worth nothing and Alice has lost the 50.

sequenceDiagram
    participant A as Alice (client)
    participant S as Solver
    participant X as Hedge venue
    participant C as Chain

    A->>C: deposit 1,000, open channel with S, commit 1,000
    S->>C: commit 5,000 to the channel
    A->>S: signed intent: buy the call, premium at most 50, valid 30s
    S->>X: hedge
    S->>A: signed fill: version 1, net A to B = 50, positions = [call]
    A->>S: co-sign version 1
    Note over A,S: more trades, all off-chain
    S->>C: every few minutes: batch checkpoint of changed channels
    Note over A,S: Friday, ETH settles at 3,200
    S->>A: version N: net A to B = 50 - 200 = -150, positions = []
    A->>S: co-sign, with withdrawable A = 1,150
    A->>C: checkpoint version N, 1,150 released to Alice's pool

If the solver vanishes on Thursday, Alice does not need it.

  1. Alice submits the last co-signed state on-chain and waits the challenge window.
  2. Alice's free cash is released when the window ends.
  3. After expiry Alice reveals the call and the oracle's Friday price. The options engine computes 200, and the channel pays it from the solver's committed collateral.

Alice's worst case is the challenge window plus the time left until expiry. If Alice vanishes instead, the solver collects what it is owed the same way.

What reaches the chain

Event Who sends it Frequency
Deposit, open channel, add collateral Either side When funding
Checkpoint of co-signed states Usually the solver Every few minutes, batched
Withdrawal Either side When taking money out
Post an unacknowledged fill Solver Only when the user is unresponsive
Challenge, respond, reveal positions, settle Either side Only in a dispute

A trade in the happy path costs no gas. My estimate for a batched checkpoint is about ten thousand gas per changed channel: one signature check and one storage update. That number needs a benchmark.

What each side is guaranteed

For the solver:

  • Collateral committed to the channel cannot leave without the solver's signature or a full notice period.
  • A signed intent stays valid until its deadline. The user cannot cancel it alone.
  • A fill becomes binding by acknowledgement or by posting it on-chain in time. No revert can undo a hedge.

For the user:

  • Nothing changes without the user's signature or a valid intent the user signed.
  • A fill the solver sat on is void if it was neither acknowledged nor posted by the deadline plus grace.
  • The solver's committed collateral backs the user's claims and the solver cannot withdraw it alone.
  • Exit never depends on the solver: challenge, wait, settle through the adjudicator.
  • The rules of an open channel cannot be upgraded underneath it.

Time is the one thing two parties cannot settle between themselves

Signatures prove who agreed. They do not prove when. A solver could sign a fill after the intent expired and claim it signed earlier.

The chain is the fallback clock. A message that depends on a deadline counts only if the counterparty acknowledged it, or if it was posted on-chain before the deadline plus a grace period. In the cooperative case nothing is posted.

A notary can serve as a faster clock later. A threshold network such as Muon could timestamp message hashes in milliseconds. It could censor or backdate, and it could never move funds or forge a trade. That is a much smaller trust than it holds today.

Three ways to build the off-chain part

A. Batched replay. The chain stays the ledger and catches up later. An operator posts batches of signed actions and the contracts execute each one. It is the InstantLayer taken further. Everything stays visible and the model is familiar. It still pays gas per trade, product logic stays on the hot path, and it still needs the channel lock so a replay cannot fail.

B. Co-signed channels with a pluggable adjudicator. The design in this note. Cheapest and fastest, and it matches the layering Naveed described. It adds two risks that do not exist today: each side must keep its own state, and each side must be reachable during a challenge window.

C. Proved batches. An operator runs the whole state machine off-chain and posts validity proofs, as a rollup or validium does. It gives the highest throughput and allows shared margin across solvers. It needs a prover, a data-availability layer and a sequencer, and it fits an exchange better than bilateral OTC.

I recommend B. The adjudicator slot leaves room for A-style on-chain engines now and C-style proofs later, so choosing B does not close the other doors.

Prior art

Hard problems

  1. State custody. If only a hash is on-chain and the user loses their copy of the positions, they cannot prove what they hold. Publishing the position data with each checkpoint solves it and keeps indexers working. Hash-only can stay as an opt-in for parties who want privacy.
  2. Liveness. A solver could open a challenge with an old state while the user is away. Frequent checkpoints shrink the exposure to the trades since the last one. Anyone can answer with a newer co-signed state, so a front-end or a watch service can defend users without holding keys. Solvers should post a bond that is slashed for submitting a stale state.
  3. Third-party fees. Two parties who co-sign could under-report fees. Fees can ride in the state as a cumulative amount per recipient. Affiliates see the intents they relay, so they can audit. Published data lets anyone recompute.
  4. Margin and liquidation. A long option that is fully paid needs neither. A short position does. The choices are capped payoffs with full collateral, a margin rule based on spot price only, or a Muon attestation of whole-book margin. Each is a different adjudicator.
  5. Many solvers competing for one order. A channel has one solver. Competition moves to the moment the user funds a channel, or the user keeps channels with a few solvers and the front-end routes between them. An allocator that co-signs locks, in the style of The Compact, can add instant competition later.
  6. The off-chain protocol becomes the product. The contracts shrink. Solvers and front-ends need a signing service, state storage, a checkpoint batcher and a watcher. That protocol needs a spec as careful as the contracts.
  7. No on-chain position objects. Trade NFTs and contracts that read positions stop working as they do now. A position can be moved into its own on-chain escrow when someone needs that.
  8. Upgrades. Pinning rules per channel protects users from admin keys. It also means a bug fix cannot be pushed into live channels. Migration has to be a co-signed close and reopen.

Decisions to make next

  1. What the periodic write contains: a hash only, the hash plus published position data, or every action replayed.
  2. Whether the first version supports margin and liquidation, or only fully collateralized positions.
  3. Who judges disputes in the first version: on-chain engines with a price oracle, or Muon attestations.
  4. Whether many-solver competition per order is needed on day one.
  5. How platform and affiliate fees are enforced.
  6. Whether the vault is immutable.
