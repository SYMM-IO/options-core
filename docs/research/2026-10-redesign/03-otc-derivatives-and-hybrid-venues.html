Hybrid derivatives venues and RFQ systems: execution, settlement and escape hatches

This note asks how venues that match or quote off-chain keep funds on-chain, how they protect the maker between quote and settlement, and how a user gets out when the operator stops. Nitro, Celer, ERC-7824/Yellow, Derive, DLCs, Perennial and StarkEx internals are covered in earlier notes. Every source was checked on 2026-10-03, and code links are pinned to the commit I read. "Unverified" marks anything I could not confirm from a primary source.

Baseline: Symmio options today

  • PartyA calls sendOpenIntent, which locks the premium (buyer) or maintenance margin (seller). A whitelisted PartyB then calls lockOpenIntent and fillOpenIntent. Expiry settlement is executeTrade with a Muon SettlementPriceSig (options intent docs). Muon prices carry a TSS Schnorr signature plus a gateway ECDSA signature (oracle docs).
  • In this repo, cancelOpenIntent moves a PENDING intent straight to CANCELED and unlocks its funds. A LOCKED intent only moves to CANCEL_PENDING (contracts/libraries/core/LibPartyAOpen.sol, cancelOpenIntent). The race window is therefore between the solver seeing a PENDING intent and its lock landing. A solver that hedges only after the lock confirms is safe, but it pays an extra transaction and a block of latency on every trade (my reading of the code).
  • Bind mode removes Muon checks between PartyA and its bound PartyB. Instant action mode lets operators batch signed sendQuote → lockQuote → openPosition into one transaction. Leaving instant mode is propose → wait → deactivate, so that it "cannot be used to front-run pending Instant Layer operations" (Binding Facet, perps v0.8.5).

Hybrid venues with an operator

Vertex, now Nado on Ink (the key reference)

Status. The Vertex team joined the Ink Foundation, the foundation behind Kraken's L2, on 2025-07-08 (Ink Foundation). Vertex wound down its EVM deployments and sunset VRTX (The Block, secondary). The successor exchange is Nado on Ink. Its contracts share Vertex's Endpoint, Clearinghouse and slow-mode code, down to the same "hardcoded to three days" comment. I read Vertex at commit e138181 (2025-05-14) and Nado at commit 380b0bc (2026-09-10).

Mechanism. An off-chain sequencer matches orders in 5–15 ms and batches them for on-chain settlement on Ink (Nado architecture). The sequencer calls submitTransactionsChecked with a strictly increasing submission index. Each batch needs a Schnorr aggregate signature from more than half of a registered verifier set (Endpoint L288, Verifier L163–175). Each MatchOrders item carries both users' signed orders, and OffchainExchange.matchOrders verifies them again on-chain (L640). Every trade is written to chain and re-executed there. Batching spreads the transaction overhead across trades, but each order still pays for its own signature check and state update.

Slow mode. Any user can call submitSlowModeTransaction directly on the Endpoint. It charges a $1 fee and appends the request to an on-chain FIFO queue with executableAt = now + 3 days (Constants L23, L50; Vertex Endpoint L331–395). The sequencer drains the queue by putting an ExecuteSlowMode item in its batch. That item always pops the head of the queue and may run before the delay expires. If the sequencer has not drained the queue after three days, anyone can call executeSlowModeTransaction() (Endpoint L199–215, L248). Nado documents this as its on-chain withdrawal path (withdrawing on-chain).

Slow mode has three limits:

  • The user-facing slow-mode types are withdraw, link-signer and deposit. There is no slow-mode path that closes a position.
  • A withdrawal still has to pass the initial-health check against the last on-chain prices (Clearinghouse L425).
  • A slow-mode transaction that reverts is consumed and dropped, not retried (Vertex L415–436).

Maker protection. The sequencer controls ordering. Withdrawals go through the same stream as matches, whether they come from the API or slow mode, so a trade the sequencer has already matched lands before any later withdrawal. Nothing is reserved on-chain per order; the off-chain engine's margin check is trusted.

Oracle. Prices arrive as sequencer-submitted UpdatePrice items, and Clearinghouse.updatePrice only checks price > 0 (L364–381). The docs name Stork, Pyth and RedStone, with updates "bundled with actions through Nado's sequencer" (oracles). I found no on-chain oracle signature check on this path. Price integrity rests on the verifier quorum.

Aevo

Aevo runs an off-chain order book and risk engine. "Once a maker and taker order gets matched, only then do they get posted" to contracts on the Aevo L2, an OP-stack rollup operated with Conduit, and Aevo pays the trading gas (Aevo docs, Exchange Structure and Layer 2 Architecture). The risk engine checks margin before an order enters the book, and the RFQ quote API reports the margin required to keep a quote open (POST /quotes). Aevo OTC is an RFQ desk for altcoin options with custom strikes and expiries up to three months, settled on the same L2. Options cash-settle in USDC against Aevo's own index, which is a filtered mean of CEX prices (same docs, Index Price).

On exit:

  • The rollup allows forced inclusion through L1 with up to a 12-hour delay.
  • Only permissioned proposers post state roots, so if they stop, "withdrawals are frozen."
  • A 4/11 Conduit multisig can upgrade the contracts with no delay (L2BEAT).
  • Aevo describes withdrawals as operator-processed, and random "flagged" withdrawals wait 60 minutes. I found no documented exchange-level forced withdrawal (unverified whether the exchange contracts have one).

Paradex, Orderly and Hyperliquid

Paradex. Paradex runs a Starknet appchain and its own sequencer. State is proven with STARKs, and data is posted encrypted, with the keys held by a three-member privacy council. L2BEAT reports "no mechanism to have transactions be included if the sequencer is down or censoring," and withdrawals freeze if the proposer fails (L2BEAT). Dated options settle at 08:00 UTC on a 30-minute TWAP of Paradex's spot oracle (dated options).

Orderly. Orderly has three layers: asset vaults on each chain, a ledger on Orderly's settlement chain, and an engine layer that runs the order book (architecture). Trades reach the ledger as batched uploads. Only the operator can submit them, and each must carry the engine's signature (OperatorManager L37–40, ImplA L83–90). Vault withdraw can only be called by the cross-chain manager (Vault L479). There is a checkEngineDown() view that returns true after 3 days without operator activity, but nothing in the repo calls it (L303–306). Users have no escape hatch.

Hyperliquid. The order book and margin engine run inside HyperBFT consensus, so validators do the matching rather than a single off-chain operator (overview). The oracle price is a stake-weighted median of prices that validators submit every 3 seconds (oracle). A withdrawal to Arbitrum needs signatures from 2/3 of validator power and then waits out a dispute period, during which lockers can freeze the bridge (Bridge2.sol). A user cannot force an exit if validators refuse to sign.

dYdX v3 on StarkEx

A user files a forced withdrawal or forced trade on L1. If the operator does not serve it within FREEZE_GRACE_PERIOD (14 days for dYdX v3), anyone can freeze the exchange. After a freeze, users withdraw with a Merkle proof, and positions close at "the average price from the last batch state update" (L2BEAT, StarkEx forced operations). A forced trade needs a counterparty's signature. dYdX v3 shut down on "October 28th" and is "processing withdrawals in escape-hatch mode" (L2BEAT; the page gives no year, 2024 is my recollection and unverified). It is the only escape hatch here that is in production use.

RFQ settlement

Hashflow. Makers stream price levels. On an RFQ, the maker has 750 ms to return a signed quote with quoteExpiry and a nonce, and the trader submits it (maker docs). Nonces must strictly increase per trader (HashflowPool L461–469). A maker's funds can sit in an "external account" that also serves other venues, so a quote can fail on-chain. A separate signQuote step accepts a market_conditions refusal, which works as a form of last look. The docs list the error but do not describe the flow fully.

Bebop. Makers sign firm quotes that BebopSettlement settles atomically, and any failed leg reverts the whole trade (settlement). Standard validity is 60 s on most L2s. "Short expiry" quotes last 3 s on Arbitrum and Base and get tighter pricing "because the market maker's risk window is smaller" (short expiry).

0x Settler. The maker signs a Permit2 PermitWitnessTransferFrom whose witness is the order (taker, amounts, partial-fill flag), with an unordered nonce and a deadline. Permit2 guarantees one fill, expiry and maker authorisation, without custody or escrow (README, RFQ).

The shared pattern. The maker signs first and the taker submits. For the quote's lifetime, the maker has given the taker a free option, which it prices through short TTLs. It hedges after the fill (Hashflow pushes trade events) or pre-hedges at its own risk. The maker ends up with an unwanted hedge only if it chose to hedge before the fill.

Last look reverses it. In AirSwap's LastLook protocol, "the client is the signer and the server is the sender" (protocols). Variational is a bilateral derivatives RFQ protocol close to Symmio's model. The taker approves the contract calls, but "no funds will actually be moved until the maker last look stage." At that stage, collateral moves from both parties into a settlement pool (RFQ, settlement pools). Unless the taker's collateral already sits in an existing pool, this is Symmio's race again.

On-chain options venues with RFQ or OTC

Rysk V12 (HyperEVM). Makers submit signed quotes with nonce and validUntil during a 2-second aggregation window. Before finalising a quote, Rysk "verifies that the market maker has sufficient USDT0 deposited" in its accounting contract. The taker confirms to Rysk's system, which settles on-chain (maker docs). Options are European, fully collateralised and physically settled on Opyn-derived Gamma contracts. The expiry price comes from Stork and Pyth (how it works). Exercise currently means contacting the team and approving funds before expiry. The deposit check happens off-chain, and who submits the settlement transaction is undocumented (probably Rysk's backend, unverified).

Premia v3. Maker quotes (QuoteOB: provider, optional taker, price, size, deadline, salt) are EIP-712 signed and published as events on Arbitrum Nova. They fill on Arbitrum One through fillQuoteOB (docs, IPoolInternal L76–106). Collateral is pulled from the maker's wallet at fill time. If the maker has moved funds, the validity check returns InsufficientCollateralBalance or InsufficientCollateralAllowance (PoolInternal L2007–2075). The settlement price is read once from a Chainlink-based adapter at maturity and cached (L1337–1346). The repo's last commit is from 2024-07.

Thetanuts V4 (Base). In OptionBook, makers sign orders and takers call fillOrder(). Each fill deploys an option contract with collateral locked. Options are cash-settled against Chainlink, and "settlement is processed daily by Thetanuts" (overview, OptionBook). The RFQ factory runs a sealed-bid auction: makers post encrypted EIP-712 offers on-chain and reveal them later, then anyone can call settleQuotation(). Collateral is "pulled from the seller at settlement, not at RFQ creation" (lifecycle). The builder guide warns that the "audit has not been completed yet."

Panoptic V2. Panoptic has no quotes. Perpetual options are built from Uniswap v3 and v4 liquidity, with streaming premia and no fixed expiry. The docs note that "oracle-free pricing does not mean there are no risk oracles": solvency checks use prices derived from the AMM (intro).

Stryke (formerly Dopex) CLAMM. Options are bought against concentrated LP liquidity, with daily and weekly expiries at 08:00 UTC (traders). Pricing is Black-Scholes with IV pushed by whitelisted ivSetter addresses (DopexV2OptionMarket L832–836).

Arrow Markets (Avalanche). Arrow sends RFQs to makers and creates the option on-chain after the best quote. At expiry, the contract "collects funds from the market makers." The docs acknowledge "default risk," so makers are not fully pre-collateralised (user flow).

Valorem. Valorem Trade is "a signature relay" for trading Valorem Clear options, "settled on chain via Seaport" (README). The repos were last pushed in 2024-01, and current status is unverified.

Paradigm. Paradigm's current docs list only Unified Markets (RFQ and order books), Delta-1 Spreads and MPX. A Market Maker Protection rule cancels a desk's orders after two fills within one second (overview, MMP). I found no current DeFi settlement product. The historical Ribbon integration used an AirSwap-derived Swap contract. Bidders signed bids off-chain, and the vault settled a batch with settleOffer(swapId, Bid[]), pulling funds from each bidder at that moment. One bidder who had moved funds reverts the whole batch (Swap.sol L194–240).

What this means for options-core

(a) The hedge-then-fill race. No venue makes the maker's hedge safe by being faster. The venues use one of two approaches instead.

  1. Operator venues control the ordering of every balance change, withdrawals included, so a matched trade always lands before a later withdrawal. Vertex/Nado puts this in contracts: a user's on-chain withdrawal enters a FIFO queue that only the sequencer can drain early.
  2. RFQ venues invert who submits. The maker signs first, the taker sends the transaction, and the maker hedges after the fill.

Where a signed quote does not reserve collateral, fills fail the same way Symmio's do: Premia makers, Thetanuts RFQ sellers, Variational takers, Hashflow external accounts and Ribbon bidders.

The pattern that fits options-core is per-channel slow mode. Collateral behind a user-signed intent can change in only two ways: by a solver-posted fill, or by a user exit request that waits in an on-chain FIFO queue for a delay D. The bound solver drains that queue in order, and anyone can execute a request once D has passed. The solver can hedge as soon as it holds the signed intent. Any exit the user files lands after the fill or cannot execute before D. The current instant-mode cooldown is a coarse version of this. Slow mode works per action, is visible on-chain and is guaranteed to execute. A cheaper alternative where a block of latency is acceptable is the RFQ direction: the solver signs a short-lived quote, the user or a relayer submits it, and the solver hedges after the fill.

(b) Per-trade gas and latency. Every operator venue I checked still writes every trade to chain: Vertex/Nado re-verify each order, Aevo posts each match and Orderly uploads each trade. Their speed comes from three things:

  • A single submitter, so there is no lock→open handshake.
  • Many trades batched into one transaction.
  • Users get confirmations from the off-chain engine before the chain sees the trade.

The equivalent step for options-core is one solver-posted batch carrying user-signed intents and fills, which replaces three transactions per trade. Skipping per-trade writes altogether needs the co-signed checkpoints from the earlier notes. Among these venues, only proof-based systems (StarkEx, Paradex) do that.

(c) Exit when the solver or operator turns hostile. Only two exits work without the operator. Vertex/Nado slow mode takes 3 days, is user-triggered, withdraws collateral only and is health-checked. StarkEx freezes after 14 days, then lets users exit with a Merkle proof, closing positions at the last price. Aevo, Paradex, Orderly and Hyperliquid have no exit a user can force at the application level.

Withdrawing free collateral is not enough while positions are open. Options have a better fallback than perps: fully collateralised positions can wait until expiry and settle from an oracle without the operator, as Premia, Thetanuts and Rysk do. options-core already has executeTrade with Muon prices and force-cancel timeouts. The exit design must guarantee that settlement, liquidation and queue execution never need the solver. Vertex's price path should not be copied, because its on-chain price is whatever the sequencer submits.

For D, Vertex chose 3 days. options-core only needs D to exceed the solver's worst-case time to post outstanding fills, plus margin for L2 congestion. That points to hours rather than days, but D is a parameter to test, not a finding.

Most important implication: make the user's exit ordered, not instant. If a user's exit request must wait in an on-chain queue that the solver drains first, every fill the solver signed earlier lands before the exit. That removes the race without trusting the solver, and once the delay passes, anyone can execute the exit.
