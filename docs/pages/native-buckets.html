Native funding buckets in the Options Diamond

Owner-local funding buckets, pinned relationships, admission checks, and integration.

Native funding buckets let each user or solver wallet keep independent funding ledgers inside the existing Options Diamond. A bucket is identified by (owner wallet, uint256 bucketId). The owner remains partyA or partyB in every intent and trade; the bucket ID selects its accounting ledger. Buckets require no account contracts or synthetic addresses.

The implementation adds ordinary facet overloads and leaves Diamond.sol unchanged. It retains the existing option pricing, oracle verification, margin model, release schedules, and clearing-house roles. It does not implement bilateral state channels or offchain challenge periods.

Choosing a bucket

Bucket IDs are local to an owner: Alice's bucket 1 and Bob's bucket 1 are different buckets. IDs need not be sequential. Bucket 0 is the existing default ledger, and old method selectors continue to use it. No implicit execution context is required.

Call createBucket(bucketId) from the owner wallet to register a bucket. Owner-directed deposits and native intent creation can register the selected owner bucket lazily. Register a solver's nonzero bucket before using it as a counterparty. Merely choosing an ID does not let another wallet withdraw or trade as its owner. ERC-20 transfers use the real payer or recipient address, never a numeric bucket ID.

PartyB registration, supported symbols, oracle configuration, release intervals, and manual synchronization remain wallet policies. Suspension and PartyB emergency checks combine the owner's global flag with the selected bucket's flag. A flag on bucket 0 does not flag a sibling nonzero bucket. The existing global action pauses still apply. balanceLimitPerUser applies to the selected balance ledger or cross entry, and maxTradePerPartyA applies to the selected PartyA bucket. They are not new aggregate limits across all buckets of a wallet.

Funding APIs

Use these ABIs at the Diamond address. Amounts accepted by deposits are raw ERC-20 units; ledger allocations, transfers, reserves, and withdrawals use the existing normalized 18-decimal amounts. The legacy overloads remain available.

Method Purpose
createBucket(bucketId) Register the caller's bucket. Repeated registration is allowed.
getBucket(owner, bucketId) / isBucketRegistered(owner, bucketId) Read the explicit identity and registration state. Bucket 0 is available by default.
deposit(bucketId, token, rawAmount) Pay from the caller wallet into its selected bucket.
depositFor(bucketId, token, owner, rawAmount) Pay into the recipient owner's selected bucket.
allocate(bucketId, token, counterpartyOwner, counterpartyBucketId, amount) Move isolated funds into one exact bilateral cross entry.
deallocate(bucketId, token, counterpartyOwner, counterpartyBucketId, amount, isPartyB, upnlSig) Release available cross funds under existing lock, margin, solvency, and oracle checks.
transferBetweenBuckets(fromBucketId, toBucketId, token, amount) Move available isolated funds between the caller's distinct buckets.
initiateWithdraw(bucketId, token, amount, recipient) Start an ordinary withdrawal pinned to the selected bucket. Later calls infer that bucket from the withdrawal ID.
getCrossBalance(owner, bucketId, token, counterpartyOwner, counterpartyBucketId) Read the exact cross entry, including signed balance, locks, and maintenance margin.
getRelationshipId(partyA, partyABucketId, partyB, partyBBucketId) Read the assigned relationship ID; zero means none has been created.
getRelationship(id) / getIntentRelationship(id) / getTradeRelationship(id) Read the immutable wallet-and-bucket association.

Explicit overloads also cover internal transfers, reserves, synchronization, counterparty binding/unbinding, virtual deposits, external transfers, and express withdrawals. External targets and express providers keep their existing wallet interfaces. See IAccountFacet (contracts/facets/Account/IAccountFacet.sol), IBucketFacet (contracts/facets/Bucket/IBucketFacet.sol), and IViewFacet (contracts/facets/View/IViewFacet.sol) for exact signatures.

A 10,000-token split

Alice deposits 10,000 tokens into bucket 7, then allocates 2,000 against Solver One's bucket 1 and 3,000 against Solver Two's bucket 2. Both solvers have the existing PartyB configuration. Before fees, premium payments, or settlement:

Alice's bucket 7 entry Token units Meaning
Isolated balance 5,000 Funds outside both relationships
Cross entry against (solverOne, 1) 2,000 Allocated exclusively to that bucket pair
Cross entry against (solverTwo, 2) 3,000 Allocated exclusively to that bucket pair
Total 10,000 Across these three accounting entries

Each side independently allocates its own collateral. Allocation is not a promise that all those units remain withdrawable: locks, maintenance margin, pending release schedules, and reserves still apply. On a cross entry, admission requires cash to cover locked + totalMM. Deallocation eligibility also depends on the existing solvency and UPNL checks. Withdrawal completion retains its existing cooldown.

For a configured local Diamond and a six-decimal collateral token, the split is:

const buckets = await ethers.getContractAt("BucketFacet", diamondAddress);
const accounts = await ethers.getContractAt("AccountFacet", diamondAddress);
const token = await ethers.getContractAt("IERC20", tokenAddress);

await (await buckets.connect(solverOne).createBucket(1)).wait();
await (await buckets.connect(solverTwo).createBucket(2)).wait();
const raw = ethers.parseUnits("10000", 6);
await (await token.connect(alice).approve(diamondAddress, raw)).wait();
await (await accounts.connect(alice)["deposit(uint256,address,uint256)"](7, tokenAddress, raw)).wait();
for (const [solver, solverBucketId, amount] of [
	[solverOne.address, 1, "2000"],
	[solverTwo.address, 2, "3000"],
] as const) {
	await (
		await accounts
			.connect(alice)
			["allocate(uint256,address,address,uint256,uint256)"](7, tokenAddress, solver, solverBucketId, ethers.parseEther(amount))
	).wait();
}

A trade against Solver One's bucket 1 cannot debit Alice's cross entry against Solver Two's bucket 2, or either wallet's unrelated bucket. A relationship has a monotonically assigned numeric ID and pins the ordered (partyA, partyABucketId, partyB, partyBBucketId) tuple. Multiple instruments and tokens between that same tuple share the relationship. Balances remain separate per token. To isolate instruments from each other, choose different bucket pairs.

Opening and closing positions

The new sendOpenIntent overload replaces the old whitelist argument with partyABucketId, partyB, partyBBucketId. The remaining parameters retain their order:

sendOpenIntent(
  partyABucketId, partyB, partyBBucketId,
  symbolId, price, quantity, strikePrice, expirationTimestamp, mm,
  tradeSide, marginType, exerciseFee, solverFee, deadline,
  feeToken, affiliate, userData
)

It requires CROSS margin and one exact solver wallet and bucket. PartyA authorizes its bucket through its wallet transaction. PartyB's wallet authorizes locking and filling that exact intent; choosing a solver does not authorize PartyA to spend the solver's other buckets. lockOpenIntent(intentId) and fillOpenIntent(intentId, quantity, price) infer both bucket IDs from the intent. Partial fills copy those IDs and the relationship to the residual intent and resulting trade. A canceled native residual does not reacquire funds.

Native admission adds cash-backing checks for the existing required costs:

  • Sending checks PartyA's collateral and fee-token entries after reserving fees, BUY premium, or SELL maintenance margin.
  • Locking rechecks PartyA's reserved backing. It creates no new solver cash reservation and does not guarantee a later fill.
  • Full or partial filling checks both sides after actual fees, premium, maintenance margin, and any pending residual reservations.
  • Voluntary close filling checks both sides after its actual accounting changes.

These checks require a nonnegative cross balance at least equal to its existing locks plus maintenance margin. They do not reserve the maximum possible option payoff. Expiry settlement and liquidation retain the protocol's signed debt recognition. Unsubmitted signed orders have no onchain reservation.

Closing, forced cancellation, exercise, and expiry use stored intent or trade IDs to recover the exact buckets. They do not require a separately selected caller bucket. Clearing flags, PartyB liquidation, unflagging, and reserve allocation take explicit wallet-and-bucket tuples; PartyA liquidation and trade closure infer buckets from the liquidation record. Fees debit the chosen PartyA bucket's exact fee-token cross entry; solver fees credit the pinned PartyB bucket. Platform and affiliate fee recipients retain their existing wallet default ledgers.

The old sendOpenIntent overload retains its bucket 0 whitelist and deferred-solver behavior. Explicit native 0/0 intents share the same default balances, nonce, and liquidation lookup with those legacy methods. Their native admission checks do not insulate the default ledger from legacy risk paths. Use nonzero buckets for separate ledgers.

Oracle signatures and clearing

For UPNL proofs with either bucket ID nonzero, LibMuon (contracts/libraries/services/LibMuon.sol) verifies:

keccak256(abi.encodePacked(
  reqId, diamondAddress, "verifyPoolUpnlSig",
  partyOwner, uint256 partyBucketId,
  counterpartyOwner, uint256 counterpartyBucketId,
  int256 partyUpnl, int256 counterpartyUpnl,
  collateral, uint256 collateralPrice,
  uint256 pairNonce, uint256 timestamp, uint256 chainId
))

The domain string verifyPoolUpnlSig retains its historical spelling for oracle wire compatibility; the terminology rename does not change signed payloads. The bucket IDs occupy the same positions in that payload.

The nonce belongs to that directed owner-and-bucket pair. Changing a bucket, wallet, Diamond, chain, token, or nonce changes the digest. Both IDs 0 retain the original verifyUpnlSig digest and legacy nonce, including explicit native 0/0 requests. Settlement-price signatures retain their existing product schema. These are Muon oracle proofs, not a new user EIP-712 channel protocol.

Bucket-aware clearing overloads flag an exact wallet-and-bucket pair and collateral. The liquidation record stores both bucket IDs and a bucket-liquidation marker. Its trade closures, confiscation, and distribution must match those endpoints, collateral, and CROSS margin; distributions may reverse the pair direction. Old confiscation/distribution overloads pass zero IDs through the same checks and cannot bypass a marked nonzero record. Unmarked legacy liquidation behavior remains confined to default ledgers. BucketLiquidationStatusChanged reports the liquidation ID, pair, bucket IDs, token, and status alongside existing events.

Integration and upgrade boundary

Native relationship trades cannot transfer ownership or mint trade NFTs. InstantLayer helper mode remains limited to default buckets. Ordinary bucket-aware external transfers and express withdrawals are supported through their existing target/provider interfaces. Token handling and trusted oracle/clearing-house assumptions remain the existing protocol's; this change adds no rebasing-token guarantee or oracle-free settlement.

This source change appends fields to mapping-backed intents, trades, withdrawals, and liquidation records, and adds scoped accounting/index mappings. Returned struct tuples therefore change ABI. Integrators must regenerate ABIs and update their decoders. It supplies no executed live-chain upgrade or migration assurance: a deployment operator must review storage compatibility, selector installation, initialization, and the deployed revision before applying it. The Diamond dispatcher itself is unchanged. BucketStorage retains the historical namespace literal diamond.standard.storage.explicitPools so the terminology rename does not change its storage location. Source type and field names use Bucket, bucketId, partyABucketId, and partyBBucketId; these naming changes are separate from the appended-field ABI changes described above.

Deployment installs the concrete AccountBalanceFacet, AccountAllocationFacet, AccountWithdrawFacet, PartyBOpenLifecycleFacet, PartyBOpenFillFacet, ClearingHouseLiquidationFacet, and ClearingHouseSettlementFacet, alongside the other facets including BucketFacet. AccountFacet, PartyBOpenFacet, and ClearingHouseFacet are abstract client ABI aggregates, not contracts to deploy. Clients use those complete ABIs at the same Diamond address; the concrete implementations serve the original and overloaded selectors. Deploy LibOpenIntentFunding first and link its address into PartyBOpenFillFacet; the deployment helper performs this step and records the link. This Solidity library executes the existing fee accounting through DELEGATECALL in Diamond storage and adds no Diamond selector. Its non-view function cannot mutate the deployed library through a direct call.

Indexers must consume the bucket-aware account, relationship, liquidation, and BucketBalanceChanged events. Existing wallet-only balance events are also emitted for nonzero buckets and cannot identify a ledger by themselves.
